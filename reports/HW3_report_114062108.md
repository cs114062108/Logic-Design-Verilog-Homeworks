### 2. Explanition of Module Implementation
This Finite State Machine is a moore machine. Its output depends on the received pattern the current state corresponds to.
```v
module Warn_Pattern (
    input  wire clk, rst_n,
    input  wire in,
    output reg  [1:0] out
);
    /*
       Code here
    */
endmodule
```

#### 2.1 Next State Logic
Use `localparam` to define the states so they cannot be overwritten via outside the module.
```v
    // ---------------------------------
    // FSM State Definitons
    // ---------------------------------
    localparam IDLE = 4'b0000; // IDLE State
    localparam S1   = 4'b0001; // Received pattern: 1
    localparam S2   = 4'b0010; // Received pattern: 10
    localparam S3   = 4'b0011; // Received pattern: 101
    localparam S4   = 4'b0100; // Received pattern: 1011
    localparam S5   = 4'b0101; // Received pattern: 0
    localparam S6   = 4'b0110; // Received pattern: 01
    localparam S7   = 4'b0111; // Received pattern: 011
    localparam S8   = 4'b1000; // Received pattern: 0110
```
Defined registers to store `state` and `next_state`.
```v
    // State
    reg [3:0] state;
    reg [3:0] next_state;

```

Designed a combinational `always` block to read the input `in` and assign `next_state` according to the current `state`.

<div style="page-break-after: always;"></div>

```v
    // ----------------------------------------------------------
    // FSM Next State Logic (Combinational)
    // ----------------------------------------------------------
    always @(*) begin
        case (state)
            IDLE: begin // IDLE State
                if (in == 1'b0) begin
                    next_state = S5; // next pattern: 0
                end else begin
                    next_state = S1; // next pattern: 1
                end
            end

            /*
                Ommitted
            */

            S8: begin   // Received Pattern: 0110
                if (in == 1'b0) begin
                    next_state = S5; // next pattern: 0
                end else begin
                    next_state = S3; // next pattern: 101
                end
            end

            default: begin
                next_state = IDLE;
            end
        endcase
    end
```
Finally, use a sequential block with non-blocking assignment to assign `next_state` to `state` when the rising edge of `clk` arrives.
```v
    // --------------------------------------
    // FSM State Register (Sequential)
    // --------------------------------------
    always @(posedge clk) begin
        if (!rst_n) begin
            state <= IDLE;
            rst <= 1'b0;
        end else begin
            state <= next_state;
            rst <= 1'b1;
        end
    end
```

<div style="page-break-after: always;"></div>

#### 2.2 Reset Mechanism
The output must be set to `2'b11` during the clock edge when input `rst_n` is set to `1'b0`, and `state` must be set to `IDLE` as a reset. Then a `rst` flag is to raised (set-low) to signal a asynchronous reset. 

Bellow is the sequential `always` block that sets the `state` to `IDLE` and signals the asynchronous reset.
```v
    // Combinational asychronous reset
    reg rst; // asynchronous rst
    
    always @(posedge clk) begin
        if (!rst_n) begin
            state <= IDLE;
            rst <= 1'b0;
        end else begin
            state <= next_state;
            rst <= 1'b1;
        end
    end
```
Then a combinational `always` block to set the when the `state` is `IDLE` and the asynchronous reset is signaled.
```v
    // ----------------------------------------------------------
    // Moore FSM Output Assignment (Combinational)
    // ----------------------------------------------------------
    always @(*) begin
        case (state)
            IDLE: begin
                if (!rst) begin
                    out = 2'b11;
                end else begin
                    out = 2'b00;
                end
            end

            /*
                Omitted
            */

            default: begin
                out = 2'b00;
            end
        endcase
```

<div style="page-break-after: always;"></div>

#### 2.3 Output Assignment
When received the pattern $1011$ or $0110$, the output should be `0'b01`, otherwise `0'b00`. Since the FSM is a moore machine, there are only two state that the output is `0'b01`. Bellow is the asynchronous `always` block the assigns the output `out` according to `state`. Since the `state` is immediatly set to `IDLE` when received the reset flag `!rst_n` at a rising `clk` edge, an asynchronous reset `!rst` only happens when the `state` is `IDLE`.
```v
    // ----------------------------------------------------------
    // Moore FSM Output Assignment (Combinational)
    // ----------------------------------------------------------
    always @(*) begin
        case (state)
            IDLE: begin
                if (!rst) begin
                    out = 2'b11;
                end else begin
                    out = 2'b00;
                end
            end

            S4: begin   // Detected 1011
                out = 2'b01;
            end

            S8: begin   // Detected 0110
                out = 2'b01;
            end

            default: begin
                out = 2'b00;
            end
        endcase
```

### 3. Testbench Design
#### 3.1 Test pattern
**Pattern 1 ($30$ ~ $90$ $\text{ns}$):** `1` $\rightarrow$ `0` $\rightarrow$ `1` $\rightarrow$ `1` $\rightarrow$ `0` $\rightarrow$ `0`
| Time | $30 \text{ ns}$ | $40 \text{ ns}$ | $50 \text{ ns}$ | $60 \text{ ns}$ | $70 \text{ ns}$ | $80 \text{ ns}$ |
| --- | --- | --- | --- | --- | --- | --- |
| `in`             | `1` | `0` | `1` | `1` | `0` | `0` |
| received pattern | $1$ | $10$ | $101$ | $1011$ | $0110$ | $0$ |
| Expected `out`   | 00 | 00 | 00 | <div style="color:#00FF00">01</div> | <div style="color:#00FF00">01</div> | 00 |
| Possible False   | 00 | 00 | 00 | <div style="color:#00FF00">01</div> | <div style="color:#FF0000">00</div> | 00 |

At $60 \text{ ns}$, the pattern $1011$ is completed, so the output `out` should be `2'b01`. However, when the `0` at $70 \text{ ns}$ arrived, that's when things might go wrong if the state transition isn't designed properly. The current `state` should be assigned to the state that represents $0110$, not $0$ or $10$. Otherwise, the output `out` would be `2'b00`, but not the correct `2'b01`.

**Pattern 2 ($80$ ~ $100$ $\text{ns}$):** `0` $\rightarrow$ `0` $\rightarrow$ `0`
| Time | $80 \text{ ns}$ | $90 \text{ ns}$ | $100 \text{ ns}$ |
| --- | --- | --- | --- |
| `in`             | `0` | `0` | `0` |
| received pattern | $0$ | $0$ | $0$ |
| Expected `out`   | 00 | 00 | 00 |

No specific pattern is received. The pattern remains $0$, and the output `out` remains `2'b00`.

**Pattern 3 ($100$ ~ $180$ $\text{ns}$):** `0` $\rightarrow$ `1` $\rightarrow$ `1` $\rightarrow$ `0` $\rightarrow$ `1` $\rightarrow$ `1` $\rightarrow$ `0` (`!rst_n`) $\rightarrow$ `0`
| Time | $100 \text{ ns}$ | $110 \text{ ns}$ | $120 \text{ ns}$ | $130 \text{ ns}$ | $140 \text{ ns}$ | $150 \text{ ns}$ | $160 \text{ ns}$ | $170 \text{ ns}$ |
| ---------------- | --- | --- | --- | --- | --- | --- | --- | --- |
| `in`             | `0` | `1` | `1` | `0` | `1` | `1` | `0` | `0` |
| `rst_n`          | `1` | `1` | `1` | `1` | `1` | `1` | `0` | `1` |
| received pattern | $0$ | $01$ | $011$ | $0110$ | $101$ | $1011$ | (--)$0$ | $0$ |
| Expected `out`   | 00 | 00 | 00 | <div style="color:#00FF00">01</div> | 00 | <div style="color:#00FF00">01</div> | <div style="color:#FFFF00">11</div> | 00 |
| Possible False 1 | 00 | 00 | 00 | <div style="color:#00FF00">01</div> | 00 | <div style="color:#FF0000">00</div> | -- | -- |
| Possible False 2 | 00 | 00 | 00 | <div style="color:#00FF00">01</div> | 00 | <div style="color:#00FF00">01</div> | <div style="color:#FF0000">01</div> | -- |

At $130 \text{ ns}$, the pattern $0110$ is completed, so the output `out` should be `0'b01`. At $150 \text{ ns}$, if next-state transition is implemented properly, it should have detected the pattern $1011$ and set the output `out` to `2'b01`. Finally, at $160 \text{ ns}$, the input `!rst_n` is set to `1'b0`, so the output `out` should be `0'b11`. If the machine is not resetted properly, it might react to the pattern $0110$ and output `2'b01`.

#### 3.2 Testbench Code Explanition
I use `@(negedge clk);`, so the inputs only change at falling clock edges, which is in the middle of a clock period. The `$monitor` outputs a log message in to the terminal using the configured format whenever any of the signals passed as a argument changes.
```v
    // the testpattern designs 
    initial begin
        //..write more code here ...//
        $display("------------------------------------------------------");
        $display("Time\t CLK\t rst_n\t in\t | \t out0 \t out1 ");
        $display("------------------------------------------------------");
        $monitor("%0dns\t %b\t %b\t %b\t | \t %02b \t %02b", $time, clk, rst_n, in, out0, out1);

        // --- Init and reset ---
        rst_n <= 1;
        in <= 0;
        
        @(negedge clk); // 5 ns
        rst_n <= 1;     // 10 ns

        @(negedge clk); // 15 ns
        rst_n <= 0;     // 20 ns

        // --- Test Pattern: 1 -> 0 -> 1 -> 1 -> 0 -> 0 ---
        @(negedge clk); // 25 ns
        rst_n <= 1;     // 30 ns
        in <= 1;

        @(negedge clk); // 35 ns
        in <= 0;        // 40 ns

        /*
            Omitted
        */

        // --- End of tests ---
        @(negedge clk); // 175 ns
        @(negedge clk); // 185 ns
        $display("------------------------------------------------------");
        $finish();
    end
```
